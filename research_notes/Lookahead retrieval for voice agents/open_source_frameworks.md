# Open-source voice agent frameworks: preemptive generation vs. speculative retrieval on interim ASR transcripts

Method note: source code was verified by shallow-cloning the default branches on 2026-11-03 (LiveKit Agents Python HEAD `8f62cab`, version string `1.8.10`, last commit 2026-11-03; LiveKit agents-js `agents/package.json` version `1.9.5`; Pipecat HEAD last commit 2026-11-03, latest CHANGELOG release `1.15.0` dated 2026-10-28; TEN Framework, Bolna, Unmute, FastRTC, Ultravox, Vocode, NVIDIA digital-human blueprint, and several small repos). File paths below are relative to each repo root on its default branch. GitHub REST "repos/*" endpoints were blocked in this session, so star counts come only from the GitHub search API (taken 2026-11-03) or from fetched repo pages. Terms: **preemptive/speculative LLM generation** means starting the LLM call before end-of-turn (EOT) is confirmed. **Speculative retrieval** means running RAG or vector search, or tool calls, on interim/partial transcripts before EOT.

## Q1. LiveKit Agents (Python/Node): what `preemptive_generation` does, when it was introduced, how it interacts with RAG hooks, and how it cancels

### Takeaway
LiveKit's preemptive generation is **on by default** in current releases. It starts only the LLM call (TTS too, if you opt in) when an STT *final* transcript arrives, or when the STT sends a *preflight/eager-EOT* transcript (Deepgram Flux style), before the turn detector commits EOT. It does **not** run on ordinary interim transcripts. RAG placed in `on_user_turn_completed` is not covered: that hook runs only after EOT, and if it changes the chat context the preemptive result is thrown away and the reply regenerated. RAG placed inside `llm_node`, as in LiveKit's own LlamaIndex example, *does* run speculatively, because `llm_node` is what the preemptive path calls. Function tools do not run speculatively: tool execution waits until the speech is scheduled and authorized.

### Cited Findings
**Introduction and history**
- PR #2728 "preemptive generation before end of user turn" (author longcw, merged 2025-07-09 into the agents 1.2 branch). Its description: "add `preemptive_generation` option to start llm generation before end of user turn, reduce the latency if the STT final transcript is faster than VAD end of speech [or] turn detection model enabled (e.g. 80~130ms on a Mac mini)". The same PR added `ChatContext.is_equivalent` — [PR #2728](https://github.com/livekit/agents/pull/2728)
- Shipped in livekit-agents **1.2.0** as `AgentSession(..., preemptive_generation=True)`. Later fixes: 1.2.2 fixed duplicated user messages after a preemptive generation was cancelled (PR #2949), and 1.2.6 added unit tests (PR #3128). Source is a mirrored changelog, not the official release page — [newreleases.io 1.2.0](https://newreleases.io/project/github/livekit/agents/release/livekit-agents@1.2.0), [1.2.2](https://newreleases.io/project/github/livekit/agents/release/livekit-agents@1.2.2), [1.2.6](https://newreleases.io/project/github/livekit/agents/release/livekit-agents@1.2.6)
- PR #5428 "fix(voice): add PreemptiveGenerationOptions for fine-grained control" was created 2026-04-13. A mirrored summary attributes the refined defaults and the options to the 1.5.4 release — [PR #5428](https://github.com/livekit/agents/pull/5428); [LiveKit community release post 1.5.3/1.5.4](https://community.livekit.io/t/released-livekit-agents-1-5-3-and-livekit-agents-1-5-4/887)
- Other related PRs: #4502 "migrate to turn_handling" (2026-01-12), which moved the option under `turn_handling`; #6537 "feat(voice): support preemptive generation for realtime models" (2026-07-24); #7991 "keep preemptive generation when a transcript only changes formatting" (2026-10-20) — [PR #4502](https://github.com/livekit/agents/pull/4502), [PR #6537](https://github.com/livekit/agents/pull/6537), [PR #7991](https://github.com/livekit/agents/pull/7991)

**Current options (verified in source)**
- `livekit-agents/livekit/agents/voice/turn.py` defines `PreemptiveGenerationOptions` with these defaults: `enabled: True`, `preemptive_tts: False` ("only LLM runs preemptively; TTS starts once the turn is confirmed"), `max_speech_duration: 10.0` ("long utterances are more likely to change"), `max_retries: 3` ("Maximum number of preemptive generation attempts per user turn"). It is configured via `AgentSession(turn_handling={"preemptive_generation": {...}})`. The old `preemptive_generation=` kwarg on `AgentSession` is deprecated in `agent_session.py` — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)
- The official docs say it "speculatively starts an LLM response before the user's end of turn is confirmed". They also say it is enabled by default, raises token usage, and is "less favorable when users speak for extended periods". If `on_user_turn_completed`, the chat context, or the tools change, "the speculative response is discarded and regenerated". The docs do not mention RAG — [LiveKit docs: audio / preemptive generation](https://docs.livekit.io/agents/build/audio/)
- agents-js (Node) has the same mechanism: `onPreemptiveGeneration`, `_preemptiveGeneration`, and the `turnHandling.preemptiveGeneration` options in `agents/src/voice/agent_activity.ts` — [agent_activity.ts](https://github.com/livekit/agents-js/blob/main/agents/src/voice/agent_activity.ts)

**Trigger point (verified in `voice/audio_recognition.py`)**
- On a `FINAL_TRANSCRIPT` STT event, `on_preemptive_generation` fires only if the accumulated transcript changed. It also requires VAD-based turn detection, an already-committed user turn, or an STT-signalled turn end. On a `PREFLIGHT_TRANSCRIPT` event, which the code describes as "used for STTs that support preflight mode, so it could start preemptive generation earlier", it fires with the preflight text appended to the committed transcript — [audio_recognition.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/audio_recognition.py)
- `INTERIM_TRANSCRIPT` events **never start** a preemptive generation. They can only kill one: if an interim arrives after a preflight ("the user kept talking after the preflight (e.g. Deepgram Flux TurnResumed)"), `on_preflight_stale` is called. That fix closed issue #7948 (2026-10-19), "Interim transcript after a preflight (Deepgram Flux `TurnResumed`) does not stop the preemptive generation" — [audio_recognition.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/audio_recognition.py); [issue #7948](https://github.com/livekit/agents/issues/7948)

**Cancellation and adoption (verified in `voice/agent_activity.py`)**
- `on_preemptive_generation` skips work when the feature is disabled, scheduling is paused, the agent is speaking uninterrupted, or the LLM is not a plain `llm.LLM`. Otherwise it cancels any earlier attempt (`_cancel_preemptive_generation()` → `speech_handle._cancel()`). It enforces `max_speech_duration` and `max_retries`, then calls `_generate_reply(..., schedule_speech=False)` on a *copy* of the chat context and stores the snapshot (`chat_ctx`, `tools`, `tool_choice`, `info`) — [agent_activity.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_activity.py)
- `on_preflight_stale` cancels the speculation when a newer interim is no longer `_transcripts_equivalent` to it. That check is a case-folded, punctuation-insensitive word-list comparison. Other cancel points: AMD verdicts, paused scheduling, a too-short interruption transcript (`min_words`), and realtime backchannel detection — same file
- At end of turn, `_user_turn_completed_impl` first runs the user's `on_user_turn_completed(temp_mutable_chat_ctx, new_message=...)`. Only then does it decide whether to adopt the speculation. It adopts only if all four hold: the transcript is equivalent, `preemptive.chat_ctx.is_equivalent(temp_mutable_chat_ctx)`, the tools are equal, and the tool_choice is equal. Otherwise it logs "preemptive generation invalidated after `on_user_turn_completed` because the transcript, chat context, tools, or tool choice changed", cancels the speculation, and regenerates — same file

**Interaction with RAG and tools**
- *Inference:* `on_user_turn_completed` is LiveKit's documented RAG injection point. Any RAG there that appends retrieved context to the chat context makes `is_equivalent` fail, so the preemptive result is always discarded and **no latency is saved**. Users hit this (see Q5, issue #4881).
- LiveKit's own RAG example `examples/voice_agents/llamaindex-rag/retrieval.py` does retrieval *inside `llm_node`*: `nodes = await retriever.aretrieve(user_query)`, then it appends the retrieved text to the system message. The preemptive path calls `_generate_reply`, which runs the pipeline's `llm_node`, so this retrieval runs speculatively on the final/preflight transcript and is cancelled along with the speech handle. *This is inference from code paths, not documented behaviour.* — [retrieval.py](https://github.com/livekit/agents/blob/main/examples/voice_agents/llamaindex-rag/retrieval.py)
- Tool execution is gated. `_pipeline_reply_task` awaits `speech_handle._wait_for_scheduled()` and `_wait_for_authorization()` before `perform_tool_executions(...)`, and a code comment says "start to execute tools (only after play())". So LLM-chosen tool calls (including RAG-as-a-tool, like `examples/homepage/knowledge_base` `lookup_product`) are **not executed speculatively**. The LLM can still *emit* the call during speculation — [agent_activity.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_activity.py)
- Issue #4219, reported on 1.2.16: when the context or tools change during preemptive generation, the turn can make two full LLM requests and double token cost. Source is a search summary of the issue — [issue #4219](https://github.com/livekit/agents/issues/4219)
- LiveKit has a "Moss knowledge base plugin" PR (#7724, 2026-10-11). I did not verify whether it does anything preemptive — [PR #7724](https://github.com/livekit/agents/pull/7724)

### Inferences
- LiveKit implements **preemptive LLM generation at "likely EOT" moments** (final STT segment or preflight), not continuous speculation over interim transcripts. It has **no built-in speculative retrieval primitive**. Developers get speculative retrieval only by accident, by putting retrieval in `llm_node`.
- Its cancellation model compares snapshots (transcript, chat_ctx, tools, tool_choice). That model is incompatible with context-injection RAG unless the retrieval happens inside the speculated branch.

### Gaps
- I could not read the PR bodies for #5428, #6537, or #7991, or the official GitHub release notes; the API was blocked. Version-to-PR mapping after 1.2.x comes from secondary mirrors.
- The default flipped to `enabled: True` at some point. The 1.2.0 release notes show an opt-in `preemptive_generation=True`. I could not pin down the exact release where the default changed (possibly 1.5.x).

## Q2. Pipecat (Daily): preemptive/speculative features and RAG integrations

### Takeaway
As of Pipecat **1.9.0 (2026-09-10)** there is a first-class **speculative inference** feature. With `enable_eager_end_of_turn=True` and `EagerUserTurnStrategies`, it answers an STT service's *eager end-of-turn* prediction (Deepgram Flux, Deepgram Flux SageMaker, Cartesia Turns), not ordinary interim transcripts. The response is held by a `SpeculationGate`, released on `UserStoppedSpeakingFrame`, and cancelled by `UserTurnResponseCancelFrame` in three cases: the user resumes, the final transcript doesn't match (`NormalizedMatch` by default), or a 5 s timeout passes. Tool calls are never executed speculatively: the speculation is withdrawn instead. There is **no built-in speculative retrieval**. The built-in Mem0 memory service does not check the `speculation` flag. Third-party `pipecat-primd` adds speculative retrieval on `InterimTranscriptionFrame`.

### Cited Findings
- CHANGELOG 1.9.0 (2026-09-10), PR #5625: "Added support for answering an eager end of turn: a response is generated from a service's predicted end of turn and held until the turn is confirmed … Turn it on with `enable_eager_end_of_turn=True` on `DeepgramFluxSTTService`, `DeepgramFluxSageMakerSTTService` or `CartesiaTurnsSTTService`, which then recommend `EagerUserTurnStrategies` … The response is discarded if the user resumes speaking or if the committed transcript differs from the predicted one, per the strategy's `match_policy` (`NormalizedMatch` by default …) … An unconfirmed turn never reaches the user or the LLM context, and tool calls are never executed for one." — [Pipecat CHANGELOG](https://github.com/pipecat-ai/pipecat/blob/main/CHANGELOG.md); [PR #5625](https://github.com/pipecat-ai/pipecat/pull/5625)
- The same release changed Flux behaviour: "the Deepgram Flux services no longer push their eager end-of-turn transcript as an `InterimTranscriptionFrame` … it now travels as an `EagerTranscriptionFrame` … Flux emits no interim transcriptions as a result". The release also added a `speculation` flag to `LLMContextFrame` — [Pipecat CHANGELOG](https://github.com/pipecat-ai/pipecat/blob/main/CHANGELOG.md)
- `src/pipecat/turns/user_stop/eager_user_turn_stop_strategy.py` (`EagerUserTurnStopStrategy`) lists three ways a speculation is withdrawn: "the user resumes speaking …", "the committed transcript differs from the eager one, per `match_policy`", and "the turn never commits within `speculation_timeout`" (default `5.0`). Its docstring adds: "Nothing the speculation produces reaches the user or the context. The inference runs against a provisional context, and its response is held by the LLM service's SpeculationGate until the turn is confirmed." — [eager_user_turn_stop_strategy.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/turns/user_stop/eager_user_turn_stop_strategy.py)
- `eager_match_policy.py` provides two policies: `ExactMatch`, and `NormalizedMatch`, which uses NFKC, casefold, and strips apostrophes and punctuation — [eager_match_policy.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/turns/user_stop/eager_match_policy.py)
- `frames.py`: `LLMContextFrame.speculation` is documented as follows: "Its response must not reach the user or the context until the turn is confirmed, and the service must not execute tool calls for it." `UserTurnResponseCancelFrame` is "A system frame so it overtakes the speculative output it cancels". `EagerEndOfTurnCancelFrame` was deprecated in 1.15.0 — [frames.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/frames/frames.py)
- `services/llm_service.py`: when a speculative inference wants a tool call, the comment reads "Tools run inside the service, so no downstream gate can undo their side effects if the speculation is discarded. Withdraw it instead; the inference that follows the committed transcript runs the call", and the code broadcasts `UserTurnResponseCancelFrame` — [llm_service.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/llm_service.py)
- `processors/aggregators/llm_response_universal.py` `_run_speculative_inference` builds a *provisional* `LLMContext` copy with the speculated user turn and pushes it downstream as `LLMContextFrame(speculation=True)`. In 1.15.0 (PR #6385) it also broadcasts `LLMContextUserTurnFrame(speculation=True)`, "so a processor that keeps the conversation should skip speculative turns" — [llm_response_universal.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/processors/aggregators/llm_response_universal.py); [CHANGELOG 1.15.0](https://github.com/pipecat-ai/pipecat/blob/main/CHANGELOG.md)
- Earlier groundwork: in 0.0.92 (2025-10-31) the Deepgram Flux service exposed `on_eager_end_of_turn` and `on_turn_resumed` events. In 1.3.0 (2026-05-28) `turn.eager_end` and `turn.resume` were surfaced via `on_turn_eager_end` — [Pipecat CHANGELOG](https://github.com/pipecat-ai/pipecat/blob/main/CHANGELOG.md)
- `InterimTranscriptionFrame` is ignored by the sentence aggregator and the LLM user aggregator. They "ignore interim and eager (provisional) transcriptions at this point", per `processors/aggregators/sentence.py`. Interims mainly drive UI/RTVI events — [sentence.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/processors/aggregators/sentence.py)
- Mem0 integration, `src/pipecat/services/mem0/memory.py`: on *every* `LLMContextFrame` it takes the latest user message, calls `_enhance_context_with_memories(...)` (retrieval), and spawns `_store_messages(...)` (a write). The `frame.speculation` flag is not checked. A grep for `.speculation` across `src/pipecat` matches only frames, the LLM service, the tone tagger, predictive delegation, evals, and turn strategies, not mem0 — [memory.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/mem0/memory.py)
- Pipecat also has "predictive delegation" (`LLMWithBackend(predictive_delegation=PredictiveDelegation(classifier))`, in the newest CHANGELOG section above 1.15.0). It runs "when a user's turn ends", racing a yes/no classifier against the frontend LLM to start a backend delegation early. This is end-of-turn speculation over the *routing decision*, not over interim transcripts — [predictive_delegation.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/pipeline/llm_with_backend/predictive_delegation.py)
- Third-party `pipecat-primd` (in rohansx/primd): "Interim transcripts (`InterimTranscriptionFrame`) trigger speculative retrieval during STT. Final transcripts (`TranscriptionFrame`) hit `/finalize`; if speculation matched the user-visible retrieval is microseconds. When the bot starts speaking (`BotStartedSpeakingFrame`) primd warms the next likely turn's scope" — [primd pipecat retriever](https://github.com/rohansx/primd)
- NVIDIA's `nvidia-pipecat` fork has "speculative speech processing" on stable interim transcripts (details in Q3).

### Inferences
- *Inference from code:* if `Mem0MemoryService` sits between the user aggregator and the LLM with eager EOT on, it would run memory retrieval on the speculative context. That part is speculative retrieval "for free". It would also *store* the provisional turn into Mem0 even if the speculation is withdrawn, which is a side-effect leak. I did not test this.
- Pipecat's design treats tool calls as unsafe to speculate and withdraws the speculation. Retrieval-as-a-tool therefore gets no speedup; only RAG done in a processor before the LLM benefits.

### Gaps
- I did not verify pipecat-flows (now merged into `pipecat.flows` per the 1.9.0 CHANGELOG) or the Gemini multimodal/RAG examples for speculative behaviour.
- I did not read the PR #5625 discussion for motivation or benchmarks.

## Q3. Other OSS frameworks (Vocode, TEN, Bolna, Ultravox, Unmute, FastRTC, Rasa, OpenAI Agents SDK, NVIDIA ACE, jambonz, Vapi/Retell)

### Takeaway
Of the other frameworks, only **NVIDIA's ACE Controller / nvidia-pipecat** (speculative LLM on stable interim ASR, opt-in) and **jambonz** (`earlyGeneration`, opt-in, on eager-EOT/final signals) ship speculative *generation*. None of them ships speculative *retrieval* on interim transcripts. TEN, Bolna, Vocode, Unmute, FastRTC and the OpenAI Agents SDK all start the LLM at end-of-turn.

### Cited Findings
- **NVIDIA ACE Controller / nvidia-pipecat (voice-agent-examples):** "Speculative speech processing reduces bot response latency by working directly on Riva ASR early interim user transcripts instead of waiting for final transcripts." The `NvidiaUserContextAggregator` "Filters stable interim transcripts (stability=1.0) for early processing". "Response generation starts after the first stable interim transcript is received". A final transcript "replaces any interim transcripts for that utterance". `NvidiaTTSResponseCacher` caches TTS "While the user is speaking" and releases it when the user stops. It is toggled by `ENABLE_SPECULATIVE_SPEECH` (default false), claims ~300 ms savings, and "only works when using Nemotron Speech ASR" (older docs say Riva ASR). RAG is mentioned only as "parallelizing LLM, RAG, and TTS services", with no retrieval mechanism described. The doc is internally inconsistent: it says "only stable interims" in one place and "both final and stable interim transcripts" in another — [SPECULATIVE_SPEECH_PROCESSING.md](https://raw.githubusercontent.com/NVIDIA/voice-agent-examples/main/docs/SPECULATIVE_SPEECH_PROCESSING.md); [HF voice-agent-examples README](https://huggingface.co/spaces/nvidia/voice-agent-examples/blob/main/examples/speech-to-speech/README.md); [ACE Controller user guide](https://docs.nvidia.com/ace/ace-controller-microservice/1.0/user-guide.html)
- **NVIDIA digital-human blueprint** (NVIDIA-AI-Blueprints/digital-human, last commit 2025-07-24): grepping for preemptive/speculative/interim/prefetch found nothing in its Python/TS — [repo](https://github.com/NVIDIA-AI-Blueprints/digital-human)
- **jambonz** (open-source CPaaS): `earlyGeneration: true` (off by default). It starts the prompt on a Krisp-pending final transcript, on Deepgram Flux `EagerEndOfTurn` (requires `eagerEotThreshold`), or on a Speechmatics turn prediction, and does not apply to other STT vendors such as AssemblyAI. "buffered tokens are released immediately" on a match. "If the user keeps talking and the transcript changes, the speculative response is discarded". Tool calls are held: "jambonz does not send them to your `toolHook` until the end of turn is confirmed and the transcript still matches". `turn_end` metrics report `latency.preflight.result` = hit/miss/pending. RAG is not addressed — [jambonz voice agents docs](https://docs.jambonz.org/guides/features/voice-agents)
- **TEN Framework** (TEN-framework/ten-framework, last commit 2026-11-03): in the example `main_python/extension.py` controllers, the ASR result is forwarded to turn detection with its `final` flag ("when getting final asr result, send to turn detection to decide if the turn is over"). In the SIP example, interim text only triggers interruption (`if event.final or len(event.text) > 2: await self._interrupt()`). I found no preemptive/speculative code. The only "prefetch" hit is a vendor metadata passthrough in `bytedance_llm_based_asr/extension.py` ("Only includes keys when present on the vendor payload (e.g. prefetch)"). RAG exists as an extension (`oceanbase_powerrag_python`) — [ten-framework repo](https://github.com/TEN-framework/ten-framework); [voice-assistant-with-turn-detection main_python](https://github.com/TEN-framework/ten-framework/tree/main/ai_agents/agents/examples/voice-assistant-with-turn-detection)
- **Bolna** (bolna-ai/bolna, last commit 2026-11-03): `optimize_latency` only sets the transcriber's `process_interim_results`. `kickoff_llm_generation` is documented as "Start the LLM turn for a final transcript", and it cancels any running LLM task "for new speech_final". RAG (`RAGServiceClientSingleton`, `rag_config`) runs inside `agent_types/graph_agent.py` at LLM time. I found no speculative retrieval — [bolna task_manager.py](https://github.com/bolna-ai/bolna/blob/master/bolna/agent_manager/task_manager.py); [graph_agent.py](https://github.com/bolna-ai/bolna/blob/master/bolna/agent_types/graph_agent.py)
- **Vocode** (vocodedev/vocode-core): the last commit is 2024-11-15, so the project is effectively dormant. Transcribers emit `is_final`, and `streaming_conversation.py` acts on final transcriptions/endpointing. I found no speculative path — [vocode-core](https://github.com/vocodedev/vocode-core)
- **Kyutai Unmute**: `unmute/unmute_handler.py` calls `_generate_response()` when STT's semantic `pause_prediction` exceeds a threshold (`if stt.pause_prediction.value > 0.6`). That is EOT-triggered with no speculative path. A 2026 arXiv paper names Unmute as an endpointer-gated cascade and proposes forecasting EOT "enabling speculative execution of LLM and TTS pipelines on partial context" (research, not shipped) — [unmute repo](https://github.com/kyutai-labs/unmute); [arXiv 2606.13450](https://arxiv.org/pdf/2606.13450)
- **FastRTC** (gradio-app/fastrtc, last commit 2026-10-21): `ReplyOnPause` runs the handler after pause detection, and grep found no interim/speculative code — [fastrtc reply_on_pause.py](https://github.com/gradio-app/fastrtc/blob/main/backend/fastrtc/reply_on_pause.py)
- **Ultravox** (fixie-ai/ultravox, last commit 2025-12-12): a speech-native model training/inference repo. It has no transcript pipeline; "prefetch" hits are only weight/dataloader prefetching — [ultravox](https://github.com/fixie-ai/ultravox)
- **OpenAI Agents SDK VoicePipeline**: with `StreamedAudioInput`, "the voice pipeline will automatically run the agent workflow at the right time", and "every detected turn triggers a separate run of your workflow". There is no built-in interruption handling and no preemptive option is documented — [OpenAI Agents SDK voice pipeline docs](https://openai.github.io/openai-agents-python/voice/pipeline/)
- **Deepgram Voice Agent API** (hosted, not OSS, for context): documents "Speculative Replies & Turn Confirmation". Per a search summary, it holds deferred function calls until the turn is confirmed. Deepgram's Flux docs recommend eager EOT especially when the pipeline includes RAG or function calling, and note roughly 50–70% more LLM calls — [Deepgram speculative replies](https://developers.deepgram.com/docs/voice-agent-speculative-replies); [Deepgram Flux eager EOT](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot)

### Inferences
- The industry "default" for speculation is now **eager-EOT-triggered LLM generation with a hold-and-release gate and deferred tools** (LiveKit preflight, Pipecat 1.9, jambonz, Deepgram). Continuous interim-transcript speculation is rarer (NVIDIA stability=1.0 interims). Speculative retrieval remains outside every mainstream framework.

### Gaps
- **Rasa voice (CALM / Rasa Pro voice)**, **Vapi** and **Retell** open-source pieces: not investigated within budget. No findings either way.
- I did not verify NVIDIA ACE source code (`nvidia_context_aggregator.py`) for in-flight LLM cancellation semantics. The doc does not describe them.

## Q4. GitHub repos implementing speculative / streaming / partial-transcript / preemptive / lookahead / anticipatory retrieval for voice

### Takeaway
Every repo that does speculative retrieval *on interim ASR transcripts* is small (≤13 stars, most 0–3): primd, Overhear, zero-latency-voice-rag, specvoice, Precog, and premove (roadmap only). The best-known related project, Salesforce **VoiceAgentRAG** (160★), prefetches *across turns*: it predicts follow-up topics after each final utterance, not on partials. Most "speculative RAG", "lookahead retrieval" and "incremental RAG" hits are unrelated (speculative decoding, RAG serving, incremental indexing).

### Cited Findings
Stars and last-push dates come from the GitHub search API on 2026-11-03 unless noted.
- **SalesforceAIResearch/VoiceAgentRAG** — 160★, pushed 2026-06-02, CC-BY-NC-4.0, paper arXiv:2603.02206. It uses a dual-agent design: a background "Slow Thinker continuously pre-fetches context into a fast cache, while a foreground Fast Talker reads only from this instant-access cache". It claims a 75% cache hit rate and a "316x retrieval speedup (110ms → 0.35ms)" on 200 queries. In `core/slow_thinker.py` the triggers are: "On UserUtterance: predicts follow-up topics, retrieves, caches; On SilenceDetected: prefetches broader context; On TopicShift…; On PriorityRetrieval: immediate retrieval for cache miss fallback". Prediction is LLM- or keyword-based (`prediction_strategy`), and it does **not** act on interim transcripts — [VoiceAgentRAG](https://github.com/SalesforceAIResearch/VoiceAgentRAG)

## Q5. GitHub issues and discussions requesting speculative retrieval or preemptive work with RAG/context changes

### Takeaway
I found no issue explicitly titled "speculative retrieval on interim transcripts". The closest are LiveKit issues complaining that context injection (the RAG pattern) kills preemptive generation, and that speculative runs can fire state-mutating tools. These are the pain points a speculative-retrieval design would have to solve.

### Cited Findings
- LiveKit **#4881** (open, 2026-02-18, by pUrGe12): "feat: Add a parameter to allow preemptive generation even after _chat_ctx modification". The author says they dynamically inject guidelines into the chat context, which "kills preemptive generation". They ask that the cancellation be optional ("It would be awesome if this cancellation was behind a config parameter") and say they would accept an occasional bad turn for lower latency. A maintainer (davidzhao, 2026-03-21) asked whether the modification happens in `on_user_turn_completed`. There is no fix yet. Quotes are via a page summary — [issue #4881](https://github.com/livekit/agents/issues/4881)
- LiveKit **#5924** (open, 2026-06-01): "[Plugin] livekit-plugins-langchain doesn't play nicely with pre-emptive generation". Quote: "Speculative runs that get discarded kick off turns that can call tools which mutate state with no rollback", and "There's no seam in the adapter to distinguish" speculative runs from committed ones. The linked open PR is #6626, "feat(llm): let an LLM declare chat() stateful" — [issue #5924](https://github.com/livekit/agents/issues/5924); [PR #6626](https://github.com/livekit/agents/pull/6626)
- LiveKit **#3414** (closed, 2025-09-12): "I think the current implementation of preemptive generation is wrong." (title only; I did not read the body) — [issue #3414](https://github.com/livekit/agents/issues/3414)
- LiveKit **#3333** (closed, 2025-09-02): "Force LLM generation to restart on context update" (title only) — [issue #3333](https://github.com/livekit/agents/issues/3333)
- LiveKit **#4219**: two full LLM requests per turn when the context or tools change during preemptive generation (via search summary) — [issue #4219](https://github.com/livekit/agents/issues/4219)
- LiveKit **#6858** (closed, 2026-08-14): "AgentTask handoff deadlocks when a preemptive generation is left parked", and **#7948** (closed, 2026-10-19): interim after preflight not stopping preemptive generation. Both are bug reports showing ongoing edge-case work — [issue #6858](https://github.com/livekit/agents/issues/6858); [issue #7948](https://github.com/livekit/agents/issues/7948)

### Inferences
- The demand signal is indirect but clear. Users who do RAG or context injection in `on_user_turn_completed` lose preemptive generation entirely. Agent-framework adapters such as LangChain/LangGraph, where retrieval and tools happen inside the "LLM", hit unsafe side effects under speculation. That points to a need for (a) retrieval inside the speculative branch with snapshot validation, and (b) an explicit speculative-vs-committed seam for tools.
