# Speculative voice retrieval still lacks a yardstick

Look-ahead retrieval for voice agents is no longer just an idea. Since October 2025, four research papers have run retrieval or tool calls on partial speech and validated the guesses at end of turn: Meta/CMU's Stream RAG, Galbraith's tool-intent stabilization analysis, an on-device speculative-execution paper, and SHANKS. None of them has a confirmed public code release. In the main open-source frameworks, nothing speculates on *retrieval*. LiveKit, Pipecat, jambonz and NVIDIA ACE all speculate on *LLM generation*, triggered by an eager end-of-turn signal or a stable interim transcript, and they deliberately block tool calls during speculation. The only open-source code that retrieves on interim transcripts lives in a handful of repos with 0 to 3 stars. The most honest of these measured a hit rate of only **0.318** on real interim transcripts. Commercial platforms run knowledge-base retrieval after the final transcript or as a model-chosen tool call. Only Sierra (in a blog post) and Deepgram (in integration guidance) put retrieval inside a speculative pattern. The realistic payoff depends on the retrieval path. For in-process vector search it is near zero. For a hosted KB it is roughly **100–300 ms**, and most of that can be captured just by starting retrieval on an eager end-of-turn signal. Only slow paths gain **0.5–2 s**: rerankers, web search, multi-hop retrieval and tools. The defensible gap is an open, deterministic, CPU-only benchmark and reference controller. It would measure when mid-utterance speculation beats eager-EOT retrieval, how much compute it wastes, and how real ASR revisions break it. That evidence is missing across all five areas surveyed.

## Four 2025–2026 papers do exactly this, and none ships code

The closest match to the target system is **Stream RAG** (Arora et al., Meta + CMU, arXiv 2510.02044). It issues retrieval and tool queries while the user is still speaking. Its training-free *fixed-interval* variant fires a query every 1 s in parallel threads. At end of speech, a "reflector" picks the earliest query whose **top-5 web documents are identical** to the final query's and terminates the rest. This is a cancel-wrong-guesses / reuse-correct-ones design, and it cut tool latency by 10.7% ([arXiv HTML](https://arxiv.org/html/2510.02044)). The *model-triggered* variant is post-trained to emit `NO_QUERY` or a new query after each 500 ms block. It runs a single tool thread, and each new query cancels the in-flight one. Negative sampling teaches it to recover from bad early guesses: accuracy is 39.8 with negative sampling versus 36.5 without, and a typical error is that the prefix "Who founded rare" first produced "Red Bull founder" ([arXiv HTML](https://arxiv.org/html/2510.02044)). On Qwen2.5-7B, accuracy rose from 26.3 to **34.2** on synthetic speech and from 26.9 to **37.4** on human speech, against an open-book baseline. Reported tool-latency savings were **20.7% on synthetic speech and 53.4% on human speech**, against a 3.37 s baseline tool path dominated by web chunking and reranking ([arXiv HTML](https://arxiv.org/html/2510.02044)). Treat the exact figures with care. The researchers found the paper reports both a 9.8% P50 first-token reduction (Section 5.3) and 20.7% (Table 1) without reconciling them. Its latencies also exclude endpoint detection. The paper reports no wasted-call counts, and the promised training code and AudioCRAG-Human release could not be confirmed ([arXiv HTML](https://arxiv.org/html/2510.02044)).

Two 2026 papers sharpen the picture. Galbraith's **"When Does Streaming Tool Use Help?"** (arXiv 2606.20113) defines *tool-intent stabilization*, the point at which a speculative query's retrieval converges on the answer-bearing result. It derives a model-agnostic bound H on hideable latency as a function of tool latency L and speaking cadence δ. With L = 600 ms and 3 words/s on 1,371 CRAG questions, **73.9% of queries admit substantial latency hiding**. On the 21.3% slice where gold evidence is verbatim and BM25-retrievable, 95.2% are streamable. Notably, the paper needs no training and runs on commodity CPU, but no code link appears on the page ([arXiv abs](https://arxiv.org/abs/2606.20113v1)). **Jung et al.** (arXiv 2610.07641, Oct 2026) build the full loop for tool calls on a real Android assistant. A predictor fires tool requests from partial ASR and caches the results. Rule-based validation drops cached results invalidated by user self-corrections. The LLM can still call tools itself, so the worst case equals the serial pipeline. Median time-to-first-audio fell from **5.79 s to 4.60 s**. The abstract reports no hit or waste rates and no code ([arXiv abs](https://arxiv.org/abs/2610.07641)). **SHANKS** (arXiv 2510.06917) reasons silently on each audio chunk and completes **56.9% of tool calls before the user finishes speaking** ([arXiv abs](https://arxiv.org/abs/2510.06917)).

The idea itself predates LLMs. Google's Interspeech 2020 **end-to-end prefetching** paper fetched assistant responses from partial recognition results. It cut latency by about 200 ms and treated prefetch rate as an explicit cost axis ([Google Research](https://research.google/pubs/low-latency-speech-recognition-using-end-to-end-prefetching/)). Amazon's 2023 **Personalized Predictive ASR** predicts the full utterance from a partial one, prefetches the response, and discards it on mismatch. A failed prefetch costs compute but no latency ([arXiv abs](https://arxiv.org/abs/2305.13794)). Neither paper is about passage retrieval from a document corpus.

The name "speculative RAG" is a trap. **Speculative RAG** (Wang et al., ICLR 2025) is about drafting answers from subsets of documents retrieved for an already-*complete* query ([arXiv](https://arxiv.org/abs/2407.08223v2)). RaLMSpec, PipeRAG, TeleRAG and ICML 2026's **Predictive Prefetching for RAG** all speculate during generation or serving, not on unfinished user input ([RaLMSpec](https://arxiv.org/abs/2401.14021); [PipeRAG](https://arxiv.org/pdf/2403.05676v1.pdf); [TeleRAG](https://syfi.cs.washington.edu/publications/telerag)). Predictive Prefetching is still useful because it publishes waste numbers. **38.7% of its triggers were false positives**; 72% of those were reused later, for about 8% net overhead ([paper notes](https://en.papernotes.org/ICML2026/information_retrieval/predictive_prefetching_for_retrieval-augmented_generation/)). The adjacent "speculate on the response" line reports useful cost and latency trade-offs. **PredGen** reports about 2x lower latency in simulation ([arXiv](https://arxiv.org/abs/2506.15556)). **Endpoint Anticipation** cut Unmute's average latency from 1,195 ms to 690 ms at **28.4% redundant compute**, with code at [bloodraven66/EndpointAnticipation](https://github.com/bloodraven66/EndpointAnticipation) ([arXiv HTML](https://arxiv.org/html/2606.13450)).

| Work | Partial-input retrieval | Final-query prediction | Cancel / validate | Waste reported | Code |
|---|---|---|---|---|---|
| Stream RAG (2510.02044) | Yes: web + KG, 500 ms / 1 s | Query rewrite from prefix | Reflector (top-5 match), newest-wins | No | Promised, unconfirmed |
| Galbraith (2606.20113) | Yes: BM25 on CRAG, CPU | No (stabilization analysis) | Analytical bound | Bound only | None found |
| Jung et al. (2610.07641) | Tool calls on partial ASR | Predictor module | Rule-based self-correction check | Not on abs page | None found |
| SHANKS (2510.06917) | Tool calls while listening | Implicit, via CoT | Not described | No | Project page only |
| Google 2020 / Amazon 2023 | Response prefetch | Amazon: yes | Discard on mismatch | Prefetch rate as cost | No |

The table exposes the hole. No paper combines **dense passage retrieval from a private corpus**, **multi-candidate prefetch**, **explicit cancellation**, and **waste accounting**, and no paper ships reusable code for any of it. The literature also warns against naive evaluation. In the inCLINC study, **humans predicted the final intent for only 66.43% of partial utterances**, and DistilBERT's "early" correct guesses often came from dataset artifacts ([ACL Anthology](https://aclanthology.org/2021.nlp4convai-1.6.pdf)). A sound benchmark should therefore measure convergence to the final result set, not accuracy against a final label, which is what Stream RAG's reflector and Galbraith's stabilization point already do.

## Frameworks speculate on the LLM at eager end-of-turn, never on retrieval

LiveKit Agents ships **preemptive generation**, enabled by default in current releases. It has run since PR #2728 (merged July 2025), which promised "80~130ms" savings ([PR #2728](https://github.com/livekit/agents/pull/2728)). Its options are verified in source: `enabled: True`, `preemptive_tts: False`, `max_speech_duration: 10.0` and `max_retries: 3` ([turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)). Preemptive generation fires on a *final* or *preflight* STT transcript. **Interim transcripts never start it; they can only cancel it** ([audio_recognition.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/audio_recognition.py)).

LiveKit's documented RAG hook is `on_user_turn_completed`. RAG placed there edits the chat context, which fails the `is_equivalent` snapshot check, so the speculative response is discarded and regenerated and **no latency is saved** ([agent_activity.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_activity.py)). Users have filed requests to make this cancellation optional ([issue #4881](https://github.com/livekit/agents/issues/4881)). They also report that discarded speculative runs in the LangChain adapter can call state-mutating tools "with no rollback" ([issue #5924](https://github.com/livekit/agents/issues/5924)). Speculative retrieval happens only by accident. LiveKit's own LlamaIndex example retrieves inside `llm_node`, and the preemptive path calls `llm_node`, so that retrieval runs speculatively and is cancelled along with the speculative reply. This is an inference from the code, not documented behaviour ([retrieval.py](https://github.com/livekit/agents/blob/main/examples/voice_agents/llamaindex-rag/retrieval.py)). Tool execution, including RAG implemented as a tool, waits until speech is scheduled.

Pipecat added first-class **speculative inference in 1.9.0** (2026-09-10). It answers an STT service's eager end-of-turn prediction (Deepgram Flux or Cartesia Turns) and holds the response in a `SpeculationGate`. The response is cancelled if the user resumes, if the committed transcript fails `NormalizedMatch`, or after a 5 s timeout. "Tool calls are never executed" for a speculative turn ([CHANGELOG](https://github.com/pipecat-ai/pipecat/blob/main/CHANGELOG.md); [eager_user_turn_stop_strategy.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/turns/user_stop/eager_user_turn_stop_strategy.py)). Pipecat also added a `speculation` flag on `LLMContextFrame`. That flag is the integration seam a retrieval processor would need. Pipecat's own Mem0 memory service does not check it, so it would plausibly both retrieve on *and store* provisional turns. This is an untested side-effect leak inferred from [memory.py](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/mem0/memory.py). Interim transcripts are ignored by the LLM aggregators. One open issue proposes speculative KV-cache prefill from interims ([issue #6511](https://github.com/pipecat-ai/pipecat/issues/6511)).

Beyond these two frameworks, **NVIDIA ACE / nvidia-pipecat** starts LLM generation on Riva/Nemotron interim transcripts with stability = 1.0. The feature is opt-in (`ENABLE_SPECULATIVE_SPEECH`, default false), claims about 300 ms, and mentions RAG only as a service to parallelize ([NVIDIA docs](https://raw.githubusercontent.com/NVIDIA/voice-agent-examples/main/docs/SPECULATIVE_SPEECH_PROCESSING.md)). **jambonz** offers opt-in `earlyGeneration` with tool calls held until the turn is confirmed, and reports hit/miss metrics ([jambonz docs](https://docs.jambonz.org/guides/features/voice-agents)). TEN, Bolna, Vocode, Kyutai Unmute, FastRTC and the OpenAI Agents SDK all start the LLM at end of turn, based on source inspection. The industry pattern has converged: speculate on the LLM at an eager-EOT moment, hold-and-release the output, and defer tools. **No mainstream framework has a speculative-retrieval primitive.**

Commercial platforms follow the same pattern. Deepgram Flux's `eager_eot_threshold` emits `EagerEndOfTurn` and `TurnResumed`, and the eager transcript is guaranteed to equal the final one if no `TurnResumed` follows. Deepgram's guide says eager processing matters most for "complex RAG ... or Function Calling" pipelines, and it saves "hundreds of milliseconds" (elsewhere "100-200ms") at the cost of **50–70% more LLM calls** ([Deepgram guide](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot/llms.txt)). Telnyx turned it on by default and reports about 150 ms median and 350 ms tail savings ([Telnyx](https://telnyx.com/release-notes/automatic-eager-end-of-turn-deepgram-flux)). ElevenLabs' `speculativeTurn` covers "LLM responses" only ([SDK types](https://cdn.jsdelivr.net/npm/@elevenlabs/elevenlabs-js@2.39.0/api/types/TurnConfig.d.ts)). Its KB retrieval runs "Every turn" or "On demand" and adds "around 250ms" ([ElevenLabs RAG docs](https://elevenlabs.io/docs/agents-platform/customization/knowledge-base/rag)). Vapi queries its custom KB on every user message and aborted Trieve retrievals after 750 ms ([Vapi](https://docs.vapi.ai/knowledge-base/migrating-from-trieve); [support thread](https://support.vapi.ai/t/28554757/knowledge-base-retrieval-aborted-request-took-too-long-waite)). The speech-to-speech APIs (OpenAI Realtime, Gemini Live, Nova Sonic, Azure Voice Live) expose retrieval only as tools the model chooses to call, which leaves the app no clean point to speculate ([OpenAI Realtime MCP](https://developers.openai.com/api/docs/guides/realtime-mcp); [Vertex Live API](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)). **Sierra** is the only vendor describing retrieval run "in parallel and speculatively" plus "predictive prefetching" (e.g., loading a known caller's orders). Its post does not say whether partial speech triggers this ([Sierra blog](https://sierra.ai/blog/voice-latency)). Contact-center agent assist is the most mature commercial form of retrieval without an explicit query: Google's Proactive Generative Knowledge Assist and Amazon Q in Connect push suggestions from live transcripts. They trigger per finalized utterance, and the human agents reading those suggestions tolerate latency measured in seconds ([Google PGKA](https://docs.cloud.google.com/agent-assist/docs/pgka); [Amazon Q in Connect](https://docs.aws.amazon.com/connect/latest/adminguide/amazon-q-connect.html)).

Open-source code that actually retrieves on interim transcripts is tiny. The closest functional competitor is **rohansx/primd**: Rust, Apache-2.0, 3 stars. It has an `observe_partial`/`finalize` API, Pipecat and LiveKit adapters, and a self-reported synthetic benchmark claiming a "100% speculative-cache hit rate", with miss and cancel semantics undocumented ([primd](https://github.com/rohansx/primd)). **Overhear**, a hackathon project, is the only one with honest measurements ([overhear](https://github.com/nikhilesh9ix/overhear)). Exact-match reuse "hit 1 of 6". A 60%-coverage prefix kept recall@5 at only **0.730 versus 0.960** for the full query. Most importantly, its authors found that "interim transcripts are revised, not merely extended", which gave a measured hit rate of **0.318 over 22 spoken queries**. Other repos are concept-stage: zero-latency-voice-rag (0 stars), specvoice and precog (speculative generation, not retrieval), and premove (a reserved PyPI name with retrieval prefetch on its roadmap) ([zero-latency-voice-rag](https://github.com/yashkum2014/zero-latency-voice-rag); [precog](https://github.com/jhammant/precog); [premove](https://pypi.org/project/premove/)). The best-known related project, **Salesforce VoiceAgentRAG** (160 stars), prefetches *between* turns rather than on partials. It reports a 75% cache hit rate and 110 ms → 0.35 ms retrievals, under a non-commercial CC-BY-NC-4.0 license ([VoiceAgentRAG](https://github.com/SalesforceAIResearch/VoiceAgentRAG)). One caveat on coverage: GitHub code search was unavailable to the researchers, so repos that implement this pattern without describing it may have been missed.

## Realistic savings: near zero for local KBs, seconds only for slow tools

Look-ahead can at best remove the retrieval step from the critical path. The real question is how long that step is compared with the time already free after the user stops talking. That free window is substantial. LiveKit's turn detector needs **295 ms at a 10% false-cutoff rate and 543 ms at 5%** ([LiveKit blog](https://livekit.com/blog/solving-end-of-turn-detection)). Median STT finalization after VAD stop ranges from about 247 ms (Deepgram Nova-3) to about 495 ms (Speechmatics) ([Daily STT benchmark](https://www.daily.co/blog/benchmarking-stt-for-voice-agents/)). Retrieval started at the last word or at an eager-EOT event therefore overlaps roughly 250–550 ms that the pipeline would spend waiting anyway. Mid-utterance speculation adds value only for retrieval longer than that window. Partials themselves are not the bottleneck: first partials arrive in about 20–130 ms, and most models are at final accuracy by then ([Artificial Analysis](https://artificialanalysis.ai/articles/new-streaming-speech-to-text-benchmark-aa-wer-streaming)). The question is semantic: whether the user has spoken the retrieval-relevant words yet.

Retrieval cost varies by orders of magnitude. VoiceAgentRAG measured **local FAISS at about 0.1 ms**, a remote Qdrant query at 97–307 ms, and a remote embedding API at about 200 ms. Its authors concede that LLM variance (500–8,000 ms) makes retrieval savings "often invisible" end-to-end ([arXiv 2603.02206](https://arxiv.org/html/2603.02206v1)). Adding a cross-encoder reranker pushed one practitioner's median retrieval from about 20 ms to **585 ms with 10 candidates and 1,258 ms with 20** ([DEV Community](https://dev.to/neeraj_singhi_golang/retrieval-latency-budgets-in-rag-pipelines-vector-search-reranking-and-the-timeout-cascade-55jk)). Web and tool paths take seconds: about 3.4 s in Stream RAG's baseline, and **3,384 ms median perceived latency on tool-call turns versus 1,392 ms overall** in a small community study ([Stream RAG](https://arxiv.org/html/2510.02044); [HF playbook](https://huggingface.co/blog/dvalle08/voice-agent-latency-playbook)).

| Retrieval path | Critical-path cost (sourced) | Hidden by starting at eager EOT / last word | Extra gain from mid-utterance look-ahead (estimate) |
|---|---|---|---|
| In-process BM25 / FAISS, local embedder | ~0.1 ms search, ~30 ms embed | All of it | ~0 ms; not worth building for |
| Hosted KB (embedding API + remote vector DB) | ~200–500 ms; ElevenLabs states ~250 ms | Most of it (250–550 ms window) | 0–250 ms |
| Hosted KB + cross-encoder rerank | ~0.6–1.3 s | Partial | ~0.3–1 s |
| Web search / multi-hop / tool APIs | ~2–5 s | Small fraction | Measured 1.2–1.8 s (Jung; Stream RAG human speech) |

The right-hand columns are this report's synthesis from the cited stage costs, not measured results. Two further discounts apply. First, the hit rate. A miss falls back to serial retrieval, so it costs no latency but saves none, and the expected saving is P(hit) × the hideable time. The published priors span a wide range: **0.318** on real revising interims (Overhear), about 66% for human intent prediction on partials (inCLINC), and **73.9%** for queries that admit hiding on CRAG under a favorable model (Galbraith). Second, lead time is short. Voice search queries average only about 2.4–3.9 words ([Mondegreen](https://arxiv.org/pdf/2105.09930); [Du & Crestani](https://strathprints.strath.ac.uk/22479/)). English questions often put the decisive entity last, so for typical short KB questions the window between "intent is predictable" and the last word is often a few hundred milliseconds. This is an inference, and no corpus study measures it directly. Human speech appears to leave more slack than TTS: Stream RAG's first-token savings were about 1.8 s on human recordings versus about 0.58 s on synthetic speech ([Stream RAG](https://arxiv.org/html/2510.02044)).

Waste is the cost side, and retrieval is cheap to waste. Speculation that saves hundreds of milliseconds typically burns **15–40% redundant compute**. Endpoint Anticipation reports 28.4%, and about 15% at a longer horizon. Predictive Prefetching reports 38.7% false triggers, netting about 8% overhead. Deepgram's eager EOT costs 50–70% more LLM calls ([Endpoint Anticipation](https://arxiv.org/html/2606.13450); [Deepgram](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot/llms.txt)). Naive re-querying every 300–500 ms over a 3–5 s utterance means 6–15 retrievals per turn. That is comparable to Google Instant's **5–7x results-page multiplier**, which Google's own executive called "pretty expensive" ([HighScalability](https://highscalability.com/how-did-google-instant-become-faster-with-5-7x-more-results/); [eWeek](https://www.eweek.com/news/google-instant-costly-as-it-prepares-for-mobile/)). A vector lookup costs a tiny fraction of an LLM call, which plausibly makes retrieval the economically correct place to speculate. That conclusion is inferred and has never been measured, which is itself part of the gap.

## Raw materials for a benchmark exist; the benchmark does not

No public benchmark scores passage retrieval on streaming spoken prefixes, except Stream RAG's AudioCRAG. Its human split has not been confirmed as released. Its protocol is easy to rebuild from public data: word timestamps from a CTC model (OWSM CTC v4), cumulative prefixes every 500 ms that drop any word straddling a block boundary, and per-stage P50/P90 latency ([Stream RAG](https://arxiv.org/html/2510.02044)). Its accuracy metric uses an LLM judge (Llama 4 Maverick), which a no-API-key project cannot use, but gold-passage labels make retrieval metrics sufficient. Several licensed candidate sources exist. **HeySQuAD** has about 76k human-spoken questions over SQuAD passages, listed as CC BY 4.0, though the live card should be confirmed ([HF](https://huggingface.co/datasets/yijingwu/HeySQuAD_human/blob/main/README.md)). **SLUE-SQA-5** has real spoken NQ, TriviaQA and SQuAD questions under CC BY-SA 4.0 and Apache 2.0 ([HF card](https://huggingface.co/datasets/asapp/slue-phase-2/blame/main/README.md)). **DSTC10 Track 2** has spoken task dialogues with an FAQ knowledge base and snippet labels. Under ASR noise, its knowledge-seeking-turn F1 falls from 0.9911 to 0.7602 ([track paper](https://cdn.amazon.science/cb/32/e83c54de4b0f9b00c023d2150258/knowledge-grounded-task-oriented-dialogue-modeling-on-spoken-conversations-track-at-dstc10.pdf); [arXiv 2209.02251](https://arxiv.org/pdf/2209.02251v1.pdf)). **τ-Knowledge** in the MIT-licensed τ²-bench offers an agentic KB domain with a voice mode ([tau2-bench](https://github.com/sierra-research/tau2-bench)). SpokenWOZ (CC BY-NC) and AmazonQAC (license unconfirmed, possibly non-commercial) work for stress tests but not for redistribution ([SpokenWOZ](https://spokenwoz.github.io); [AmazonQAC](https://huggingface.co/datasets/amazon/AmazonQAC/blame/main/README.md)).

These sources have two blind spots. SQuAD-derived questions were written while looking at the passage, so their prefixes overlap lexically with it and look unrealistically easy to retrieve on. NQ, TriviaQA and CRAG questions are more natural. More important, **no public dataset ships real interim ASR hypotheses, with their revisions, together with timestamps**. Forced-aligned truncations of final transcripts lack the "flicker" that sank Overhear's hit rate. Google's RNN-T study measured **0.04–0.37 unstable partial words per final word**, depending on domain and emission interval ([arXiv 2006.01416](https://arxiv.org/abs/2006.01416)). A credible benchmark therefore needs two conditions: an oracle-prefix condition and a replayed-streaming-ASR condition with real revisions.

Metrics can be borrowed rather than invented. Hardware prefetching contributes a triad: *accuracy* (useful prefetches / issued prefetches), *lateness* (useful prefetches that arrive too late), and *pollution* (prefetch-induced misses). It also contributes an empirical warning: below **40% accuracy, stream prefetching always hurt performance**. Feedback-Directed Prefetching throttles aggressiveness per interval using accuracy thresholds of 0.40 and 0.75 ([Srinath et al., HPCA 2007](https://users.ece.cmu.edu/~omutlu/pub/srinath_hpca07.pdf)). Chrome adds confidence tiers (preconnect at about 30%, prerender at about 50%) and caps of two concurrent speculations with FIFO cancellation ([Chrome](https://developer.chrome.com/blog/prerender-pages/)). Simultaneous translation contributes Average Lagging and **Normalized Erasure**, with NE < 0.2 as the low-revision operating point ([STACL](https://arxiv.org/abs/1810.08398); [Arivazhagan et al.](https://arxiv.org/abs/2004.03643)). Query auto-completion contributes MRR as a function of prefix length, and evidence that hybrid context-plus-popularity predictors beat either signal alone, by +31.5% MRR ([Bar-Yossef & Kraus](https://www.ee.technion.ac.il/people/zivby/papers/consuggest/consuggest.pdf)). **Rank-Biased Overlap** gives a top-weighted stability score between successive prefixes' result lists ([Webber et al.](https://dl.acm.org/doi/10.1145/1852102.1852106)). Combined, these define what no paper reports. The benchmark would score six things: recall@k parity at EOT against retrieval on the full transcript; ready-by-EOT rate and lead-time distribution; a convergence curve of RBO against the fraction of the utterance heard; FDP-style accuracy, coverage, lateness and pollution; retrieval erasure; and wasted retrievals per turn.

## The defensible gap: an offline benchmark plus a cost-aware controller

The territory is crowded in some places and empty in others. Speculative *LLM generation* at eager EOT is solved and shipping, in LiveKit, Pipecat, jambonz, Deepgram and ElevenLabs, so building another one would be pointless. Speech-native, *trained* streaming RAG belongs to Meta/CMU, and it needs GPUs and LLM judges. *Cross-turn* prefetch has Salesforce's (non-commercial) reference. What is missing is everything a practitioner needs before turning speculation on. No open dataset of revising interim transcripts with gold passages exists. No harness measures whether mid-utterance speculation beats simply retrieving on eager EOT for a given retrieval-latency profile. No framework-agnostic controller exists with multi-hypothesis prefetch, explicit commit and cancel tests, side-effect safety, and published waste. primd is the nearest code, but it is tiny and backed only by a synthetic benchmark. Galbraith's paper is the nearest evaluation methodology, and it is CPU-based and training-free but has no code. Either could close part of the gap, which is the main competitive risk. Two other risks are the eventual release of AudioCRAG-Human and the Stream RAG code, and the fact that Pipecat's `speculation` flag makes a built-in retrieval processor a small step for its maintainers.

The most defensible positioning is **benchmark first, library second**: "the open, reproducible yardstick for look-ahead retrieval, plus a reference controller that passes it." This fits the constraints well, because every required component runs on CPU without LLM keys. BM25 and small embedding models stand in for the retriever. Real streaming ASR is run once, offline, to generate interim hypotheses, which are cached as dataset artifacts so CI never runs ASR. A **virtual clock** replays word timestamps and injects configurable retrieval-latency profiles, so results transfer to hosted, reranked and web-search stacks without needing that hardware. Scoring uses gold passages instead of LLM judges, which makes every number deterministic and verifiable offline. The baselines should include the industry status quo as well as the research designs. The project would compare retrieve-at-final, retrieve-at-eager-EOT (the bar to beat), Stream RAG–style fixed-interval fan-out with a top-k reflector, newest-wins single-thread re-querying, an RBO-stability gate with hysteresis, a wait-k content-word gate, QAC-style multi-hypothesis completion capped at two concurrent queries, and VoiceAgentRAG-style cross-turn prefetch. The library would then expose the winning policies through the seams that already exist: Pipecat's `speculation` flag and LiveKit's `llm_node`. It would be read-only by construction, so it avoids the tool side-effect and context-invalidation problems that users report in LiveKit issues #4881 and #5924.

The project should also commit to publishing negative results. Given the evidence above, the likely headline is that look-ahead buys almost nothing for local KBs, about 100–250 ms beyond eager EOT for hosted KBs, and around a second for rerankers, web search and tools. Real ASR revisions roughly halve the hit rate compared with clean prefixes. A project that says so with reproducible numbers will be more credible, and more widely cited, than one promising "zero-latency RAG."

## Conclusion

The field has an inverted shape. Engineering effort has gone into speculating on the most expensive component, the LLM, at the latest possible moment, eager EOT. The cheapest component to speculate on, retrieval, remains serial everywhere except in research prototypes and weekend repos. The reason is not that the idea is unknown. Nobody has shown practitioners when it pays. The published evidence suggests the benefit is real but concentrated in slow retrieval paths, and most of it for ordinary KB-RAG is available simply by starting retrieval at the eager end-of-turn signal. Mid-utterance speculation is a specialist tool for stacks where retrieval takes longer than the 250–550 ms end-of-turn window.

For a project, that makes measurement itself the scarce asset. An offline, CPU-reproducible benchmark with real revising interim transcripts and prefetch-style waste metrics would answer the question frameworks and vendors currently answer with anecdote. A small read-only controller validated on that benchmark is the natural thing for Pipecat or LiveKit users to adopt. Its lasting value lies in the benchmark data and the decision rule ("speculate only when retrieval latency exceeds X and predicted stability exceeds Y"), because a framework vendor could replicate the code in a release cycle but not the evidence. The main uncertainties to resolve early are three: whether Stream RAG's code and AudioCRAG-Human appear; whether primd matures; and whether the roughly 0.3–0.75 hit-rate range on real interim transcripts holds beyond the small samples behind it.
